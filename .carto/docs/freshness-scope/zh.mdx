Carto 分开回答两个问题。**新鲜度**判断页面是否仍与其声明来源的实际字节一致；**覆盖率**判断有哪些未被忽略的文件尚未归属任何页面。`sync` 本身不会审阅文案；只有编写任务的正确性与展示门禁都通过后，它才为内容盖章。`skills/carto/SKILL.md:57-60`


## 新鲜度比较的是文件内容

每个来源的指纹都由文件字节计算 SHA-256，再截取前 16 个十六进制字符。路径、修改时间和 Git 状态都不参与这次计算。

packages/core/src/hash.ts:1-10

文件存在时，Carto 会计算当前指纹并与已存指纹比较；文件不存在则单独判定。在页面层面，系统按 `missing` > `stale` > `unsynced` > `fresh` 的优先级取所有来源中最严重的状态；因此，没有来源的节点保持 `fresh`。

packages/core/src/status.ts:5-52

| 状态 | 来源判定规则 | 对页面的影响 | 应对方式 |
| --- | --- | --- | --- |
| `fresh` | 文件存在，当前哈希与已存哈希相同。 | 不会带来新鲜度问题。 | 无需处理。 |
| `unsynced` | 文件存在，但尚无已存哈希。 | 优先级高于 `fresh`。 | 审阅新纳入的依据，再同步该页面。 |
| `stale` | 文件存在，但当前哈希与已存哈希不同。 | 优先级高于 `unsynced`。 | 检查来源改动、更新文案，再定向同步该页面。 |
| `missing` | 读取来源时得到 `ENOENT`。 | 是页面能取得的最高优先级状态。 | 先修正来源归属或恢复文件，不要直接写入同步状态。 |

这种聚合规则对多来源页面尤其重要：只要一个来源缺失，节点就是 `missing`，即使其他来源处于 `stale` 或 `unsynced`。报告仍保留每个来源各自的状态，因此不会丢失具体问题的位置。

## 覆盖率是考虑忽略规则的集合差

覆盖分析通过一条考虑忽略规则的集合流水线得到 `uncovered`：

```text
documentable = 遍历 codeRoot
  → 只保留普通文件；路径统一为 POSIX
  → 移除内建排除项
  → 应用 .gitignore + .cartoignore
  → 移除嵌套的文档根目录

covered = 所有 node.sources 规范化后的并集
uncovered = sort(documentable − covered)
```

`packages/core/src/coverage.ts:11-67`

因此，覆盖率衡量的是“有没有页面负责”，而不是文案质量或新鲜度。某个来源只要已被声明，即使所属页面过期，也仍算已覆盖；被忽略规则移除的文件则不进入分母，不能理解为“已覆盖”。修改 `sources` 会同时改变集合差和新鲜度准星，只应发生在真实的职责迁移中。

## CLI 把状态落实为退出策略

`carto status` 会输出每个节点，只展开非 `fresh` 的来源行；若存有提交锚点，还会显示 `(was …)`。对于状态为 `stale` 的节点，它会给出定向同步提示。只要存在任何非 `fresh` 节点，命令就以非零状态退出，因此新鲜度可以直接充当命令行门禁，而不只是展示信息。

packages/cli/src/commands/status.ts:1-33

`carto coverage` 会输出已覆盖文件数、文件总数以及排序后的未覆盖清单；没有任何可纳入文档的文件时，比例显示为 `100.0%`。默认情况下，存在未覆盖文件只作提示；只有传入 `--fail-on-uncovered`，该情况才会导致非零退出。

packages/cli/src/commands/coverage.ts:1-27

三种调用对应不同策略：

| 调用 | 通过条件 | 失败后应处理什么 |
| --- | --- | --- |
| `carto status` | 所有节点均为 `fresh`。 | 刷新、同步或修复报告中的非新鲜节点。 |
| `carto coverage` | 清单读取和覆盖分析成功；默认不因未覆盖文件失败。 | 修复命令错误；若项目策略要求完整覆盖，再为文件分配页面。 |
| `carto coverage --fail-on-uncovered` | 未覆盖集合为空。 | 为文件建立依据归属，或明确忽略不需要文档化的文件。 |

## 定向刷新只确认已审阅的工作

状态报告发现过期页面后，按以下顺序处理：

```text
carto status
    ↓ 只选取本次范围内的节点 id
查看来源差异（无法比较时重新通读来源）
    ↓ 根据已审阅依据更新所有语言版本
carto sync <id> [<id> ...]
    ↓
carto validate
    ↓
carto status  →  本次处理的 id 全部 fresh
```

具名 id 就是审阅边界：定向同步只写回核心操作判定为有变化的节点。不传 id 时只选择 `unsynced` 来源，绝不会刷新 `stale` 页面，因此裸 sync 不能代替对陈旧答案的审阅。验证与最终状态检查结束后，所选范围之外的问题仍保留原有信号。`packages/cli/src/commands/sync.ts:5-30` `packages/core/src/manifest.ts:7-9,171-238` `skills/carto/SKILL.md:64-70` `skills/carto/SKILL.md:112-139`

Git 提交锚点采取尽力而为策略：Carto 执行 `git rev-parse HEAD`，不显示 Git 的标准错误；命令失败或没有得到值时返回 `undefined`。

packages/cli/src/git.ts:1-9

提交值只是审阅来源差异时的辅助锚点，不是新鲜度依据。状态报告会携带并显示它，但分类仍只由文件是否存在以及内容哈希决定。代码根目录不在 Git 仓库中、来源尚未跟踪，或历史经过 rebase 后，差异锚点可能不可用，却不会削弱字节级比较。

## 改动应落在哪里

- 文件、哈希、配置约束或底层同步选择属于[文档模型](carto:document-model)。
- 编写者如何圈定范围、审阅依据、维护多语言内容并完成校验，属于[编写工作流](carto:authoring-workflow)。
- 命令注册、校验门禁以及单次调用行为属于 [CLI 工作流](carto:cli-workflow)。

边界应保持清楚：status 观察依据是否变化，coverage 观察归属是否完整，定向 sync 则记录一个已经完成审阅的决定。
