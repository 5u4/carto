一次 Carto 编写任务的起点是开发者给出的范围，而不是漫无目的地扫描目录。编码代理负责理解与取舍：确定长期有效的开发者问题、沿可执行路径取证、选出足以让答案失效的文件，并分别写好每种已声明的语言版本。CLI 负责确定性的账务工作：报告新鲜度与覆盖率、为已审阅的来源计算哈希，并检查结构和链接。核心契约与生成流程共同界定了这些职责。`skills/carto/SKILL.md:17-20` `skills/carto/SKILL.md:41-55` `skills/carto/SKILL.md:83-89` `skills/carto/SKILL.md:91-106`

## 动笔前先锁定范围

首先通过帮助信息探测已安装 CLI 的真实命令面，再在选择检查或编写分支前确认 `carto.json` 已存在。若文件缺失，代理应停止，并请请求者自行运行 `carto init`；初始化始终由请求者负责。即使 `.carto/docs/` 尚未创建，只要 manifest 存在就满足此前提；后续 Carto 命令读到无效 manifest 时，仍应按配置错误处理。创建或刷新文档必须有明确范围；单纯查看状态或覆盖率则无需编写范围。`skills/carto/SKILL.md:22-55`

收到编写请求后，先运行 `carto status` 与 `carto coverage`，再将结果与请求范围取交集。前者给出可能需要刷新的陈旧节点，后者给出尚未分配给节点的源文件；如果交集为空，就结束任务，不为改写而改写。普通的新建或刷新可以直接继续；删除节点或来源、修改 id、调整父子关系、大规模重分配来源，或范围仍不明确时，则必须通过安全检查点，在改文件前取得明确批准。`skills/carto/SKILL.md:61-82`

因此，[新鲜度与来源覆盖率](carto:freshness-scope)只是测量结果，并不替代理做编写判断：CLI 能指出哪里陈旧或未覆盖，代理仍要判断这些事实是否属于本次开发者问题。`skills/carto/SKILL.md:64-69`

## 从可执行证据规划答案

每个节点只回答一个核心开发者问题，并用其中适用、且有助于形成可操作答案的所有权、入口、流程、契约、约束与改动面来界定问题。合格的节点从一项端到端职责或流程出发，而不是照着模块或目录拆页；只有相邻问题本身值得独立解答，在所有者、入口、契约、流程、不变量或改动面上存在实质差异，并值得独立导航或独立判定新鲜度时，才应拆分。`skills/carto/references/documenting.md:7-32`

在起草任何语言版本前，代理要读完实现、真实调用方、下游副作用、共享契约和可观察路径。事实与跨模块关系必须由真正建立它们的表达式支撑，不能只凭名称或附近的声明推断。语言无关的证据计划应记录核心问题、子问题、视图、关系、精确锚点和 `carto:` 目标；随后再从“哪些文件的变化会推翻该计划”反推 `node.json.sources`。`skills/carto/references/documenting.md:34-95`

所以，来源集合是新鲜度的准星，不是顺手收集的文件清单。每个来源都必须在每种语言里贡献至少一个精确锚点，而导航链接永远不能充当证据。磁盘契约把三类职责分开：`sources` 驱动新鲜度判断，字面锚点支撑文字事实，`carto:` id 则负责导航。`skills/carto/SKILL.md:186-261`

## 依同一计划分别写好每种语言

每种已声明的语言版本都从同一份证据计划直接创作，而不是逐句互译。各版本保留相同的核心问题、受支持事实、精确来源锚点、`carto:` 目标和视图用途；为了符合本地技术读者的习惯，标题、顺序、术语和句式可以不同。起草过程中新增的事实也必须回到可执行证据核验，必要时还要扩充 `sources`。`skills/carto/references/documenting.md:97-127`

视图只负责呈现有助于子问题的代码形状。代理应优先使用经过核验的文本结构，避免用长段落重述同一分支或流程，删掉装饰性的清单，并逐一核对标签和连线。`skills/carto/references/presenting-code.md:9-18` 来源锚点应放在视图相邻的说明文字中，而不是塞进图内；不同语言要保留等价的视图用途与关系。`skills/carto/references/presenting-code.md:109-122`

下面的控制流本身也遵守这一规则。证据计划的内容、各语言事实对齐且表达自然的要求、执行顺序——尤其是先审计再同步、验证后仍要定向检查状态——以及对验证所报错误的修复，都来自编写与生成契约。`skills/carto/SKILL.md:57-124` `skills/carto/references/documenting.md:71-79` `skills/carto/references/documenting.md:99-108` `skills/carto/SKILL.md:313-330`

```text
限定范围的请求
  ├─ status + coverage ──> 将客观结果与范围取交集
  ├─ 安全检查点 ─────────> 仅在结构风险或歧义时等待批准
  ├─ 证据计划 ───────────> 问题 + 关系 + 锚点 + 视图
  ├─ node.json sources ──> 可能使答案失效的文件
  ├─ 编写全部语言版本 ───> 事实对齐，表达各自自然
  ├─ 聚焦审计 ───────────> 只给发现；修正已接受的正确性问题
  ├─ sync <id...> ───────> 只标记已审阅节点
  ├─ validate ───────────> 修复点名的结构/树/链接/语言错误
  └─ status ─────────────> 仅当范围内所有 id 都为 fresh 才结束
```

## 第一次同步前只做一次聚焦审计

编写完成后，由一名全新的只读审阅者接收完整的范围内节点集合、默认语言页面、所有已列出、页面直接引用或用于证明关系的源文件，以及审计量表。审阅者只检查证据正确性，只返回发现，不编辑也不同步。`skills/carto/references/auditing.md:3-18`

这次检查刻意保持窄范围：只报告缺失或不承重的来源、没有证据的跨文件关系，或被可执行代码直接否定的事实、流程、视图和复现结果。每条发现必须指出页面精确位置、能证明问题的来源锚点和最小事实修正；文风、术语、展示方式、语言一致性和完整性建议不在审计范围内。`skills/carto/references/auditing.md:20-47`

代理逐条接受发现，或以精确代码证据驳回；被接受的事实修正要同步应用到所有语言，并重新对齐锚点和 `sources`。完成这些动作后，`carto sync` 才能为文档盖章。只有当发现迫使页面主题或主流程大幅重写时，才需要再次审计。`skills/carto/SKILL.md:91-102`

## 闭合定向的 sync–validate–status 循环

使用 `carto sync <id> [<id> ...]`，只传入已经审阅的 id。显式命名节点会记录其当前来源哈希，并在可获得时记录当前提交，又不会抹掉范围外节点的新鲜度信号。随后运行 `carto validate`；修复它明确指出的 schema、树、语言、来源或逻辑链接错误，仅重新同步发生变化的 id，再次验证。最后必须运行 `carto status`：验证成功时，范围外页面仍可能陈旧；而本次接触的每个 id 都必须单独回到 `fresh`。`skills/carto/SKILL.md:104-144` `skills/carto/SKILL.md:210-217` `skills/carto/SKILL.md:313-330`

各命令的行为与失败边界归 [CLI 工作流](carto:cli-workflow) 说明。本页的编写闭环补上确定性命令无法承担的判断：问题是否值得长期维护、证据是否承重、文字是否准确，以及结构改动是否安全。`skills/carto/SKILL.md:17-20` `skills/carto/SKILL.md:104-144`

## 职责边界

这套流程把“作决定”和“做检查”分开，而不是把自动化当作作者：请求者划定范围并批准高风险结构改动；编码代理检查可执行证据并编写完整节点；全新审阅者执行聚焦的正确性复核；CLI 则提供确定性的同步、验证和新鲜度关卡。`skills/carto/SKILL.md:50-124` `skills/carto/references/documenting.md:34-127` `skills/carto/references/auditing.md:6-47`

| 参与者 | 负责 | 不可替代 |
| --- | --- | --- |
| 请求者 | 定义范围；批准有歧义或会破坏既有结构的改动。 | 证据选择或 CLI 检查结果。 |
| 编码代理 | 理解范围，设计节点问题与边界，检查可执行路径，推导 `sources`，分别编写全部语言，并修正已接受的审计发现。 | 哈希计算、链接解析或新鲜度计算。 |
| 全新只读审阅者 | 对完整的范围内默认语言文档检查来源/锚点/关系以及事实/流程的正确性。 | 编辑、同步、文风审阅或其他语言审阅。 |
| Carto CLI | 报告状态和覆盖率，为显式审阅过的 id 盖章，验证 schema/树/语言/链接，并报告最终新鲜度。 | 决定页面应教什么，或判断证据是否足以支撑其心智模型。 |

如果源文件拆分、职责迁移、入口或契约变化，就要在定向同步前重做相关证据计划并更新每种语言；删除陈旧来源并不能解决问题。`skills/carto/SKILL.md:140-144` `skills/carto/references/documenting.md:81-113` 更广泛的确定性测试与模型评测边界另见[验证体系](carto:verification)。
