---
title: CLI workflow
description: How one Carto invocation is dispatched, initialized, and validated through deterministic gates.
---

A `carto` invocation has a deliberately thin command layer. The executable selects a command, `init` establishes a valid documentation root, and `validate` gathers structural and content failures before deciding the process result. The CLI delegates document parsing, freshness, tree, federation, and link semantics to core rather than reimplementing them.

## Executable dispatch

The executable entry in `packages/cli/src/index.ts` starts with a Node shebang, imports the command definition, and gives it to Citty's `runMain`; argument parsing, help, and subcommand selection therefore all begin at one entry point. `packages/cli/src/index.ts:1-5`

The registry exposes seven responsibilities and no hidden default workflow. `packages/cli/src/main.ts:1-20`

| Command | CLI responsibility | Deeper behavior lives in |
| --- | --- | --- |
| `init` | Create the documentation root after validating its proposed config | This page |
| `status` | Report source freshness | [Freshness and scope](carto:freshness-scope) |
| `sync` | Bless reviewed sources in the requested scope | [Freshness and scope](carto:freshness-scope) |
| `coverage` | Report source files not assigned to nodes | [Freshness and scope](carto:freshness-scope) |
| `validate` | Aggregate schema, tree, sync, locale, and link findings | This page |
| `build` | Request a production site build | [Rendering pipeline](carto:rendering-pipeline) |
| `preview` | Request the local rendered-site workflow | [Rendering pipeline](carto:rendering-pipeline) |

This split is a maintenance boundary: changes to dispatch belong in `main.ts`; changes to manifest representation belong in the [document model](carto:document-model), navigation and cross-doc-set resolution belong in [navigation and federation](carto:navigation-federation), and site production belongs in the rendering pipeline.

## Initialization is validate-before-write

`carto init` uses the current working directory as the doc root and first checks for `carto.json`. If it exists, the command refuses to overwrite it and exits before creating or changing the scaffold. `packages/cli/src/commands/init.ts:13-19`

For a new root, initialization follows this order:

1. Split the comma-separated locale argument, trim each item, and discard empty items.
2. Build a version-1 config with the selected default locale, an empty federation list, and `codeRoot` only when supplied.
3. Run core's `parseConfig` on the proposed config. A `ManifestError` becomes a user-facing error and exit 1, so invalid input cannot reach the filesystem writes. `packages/cli/src/commands/init.ts:28-32`
4. Create `.carto/docs/`, serialize `carto.json`, and create `carto.config.mjs` only if that optional customization file does not already exist.

The validate-before-write sequence and conditional config write are explicit in `packages/cli/src/commands/init.ts:20-41`. The generated module is intentionally a minimal typed Starlight customization stub, not another source of manifest data. `packages/cli/src/commands/init.ts:54-61`

:::note[Ownership boundary]
Initialization chooses defaults and controls scaffold safety. The accepted config shape, canonical paths, parsing, and serialization are core contracts described by the [document model](carto:document-model).
:::

## Validation call tree

Validation has two phases: prerequisites that must succeed before meaningful checks can run, followed by deterministic collection of all independent findings.

```text title="carto validate"
readManifest(current directory)
├─ failure → print one error, exit 1
└─ loadGraph(current directory)
   ├─ failure → print one error, exit 1
   └─ collect findings
      ├─ checkTree(nodes) → error or warning by issue severity
      ├─ verify configured home id exists → error
      ├─ statusReport(manifest, resolved code root)
      │  ├─ unsynced → error
      │  ├─ stale → warning
      │  └─ missing source → error
      └─ for every node × configured locale
         ├─ missing locale file → error
         └─ read MDX
            └─ extract carto targets
               └─ resolveCartoLink(target, manifest + locale + federation)
                  └─ resolution failure → error

print warnings
├─ any errors → print every error, exit 1
└─ no errors → print "validate: ok"
```

Manifest and graph loading are early gates because downstream checks need those objects; their failures are normalized and returned immediately. Once both are available, tree issues, the `home` target, and freshness states are appended to separate error and warning arrays instead of failing at the first finding. `packages/cli/src/commands/validate.ts:19-60`

Locale completeness is a Cartesian check: every manifest node must have a file for every configured locale. Existing files are read independently, and every extracted logical link is resolved using that file's locale plus the loaded federation context. This makes a missing translation or a broken link in only one locale a validation error rather than a fallback. `packages/cli/src/commands/validate.ts:62-75`

Finally, warnings are emitted first. Any accumulated error is then emitted and causes exit 1; with no errors the command prints `validate: ok`. An empty node set gets an informational message. `packages/cli/src/commands/validate.ts:77-84`

### What blocks the invocation

| Finding | Result | Why the distinction matters |
| --- | --- | --- |
| Tree issue marked `error` (including a cycle) | Error | Navigation cannot be trusted |
| Dangling parent marked `warning` | Warning | A subtree may be authored before its parent |
| Unknown configured `home` | Error | Root navigation would target no node |
| Unsynced node | Error | Its source evidence has not been blessed |
| Stale node | Warning | Review is required, but unrelated scoped work can still validate |
| Missing source | Error | A declared evidence file cannot be checked |
| Missing locale MDX | Error | The node is incomplete for the configured locale set |
| Unresolvable `carto:` target | Error | Local or federated navigation would be broken |

`validate` does not decide tree severity, freshness state, or logical-link meaning itself. It consumes those typed results and decides only how a CLI run reports and exits. Follow the underlying state rules in [freshness and scope](carto:freshness-scope) and the resolution failure modes in [navigation and federation](carto:navigation-federation).

## Link extraction and delegation

The CLI's extractor scans Markdown link destinations that use the `carto:` scheme, collecting each non-whitespace target up to the closing parenthesis in encounter order. It does not interpret ids, fragments, or federation aliases. `packages/cli/src/links.ts:1-8`

That narrow extraction step is followed by `resolveCartoLink` for each target. Validation supplies the current manifest and locale, and, when a federated graph exists, its hash and alias indexes plus the site's default locale. The resolver returns typed failures that the CLI turns into stable messages for unknown ids, unsupported or unknown federation aliases, missing federated ids, and malformed targets. `packages/cli/src/commands/validate.ts:30-36` `packages/cli/src/commands/validate.ts:69-73` `packages/cli/src/commands/validate.ts:110-124`

This boundary keeps extraction mechanical and resolution authoritative: change which Markdown destinations are discoverable in `links.ts`, but change the semantics of a discovered `carto:` address in [navigation and federation](carto:navigation-federation). Rendering later rewrites successfully resolved logical targets; that transformation belongs to the [rendering pipeline](carto:rendering-pipeline).

## Change surfaces

- Add, remove, or rename a top-level command in `main.ts`, keeping the command module responsible for its own orchestration.
- Change initialization ordering in `init.ts` only while preserving refusal-before-write and config-validation-before-scaffold invariants.
- Add a validation gate in `validate.ts` when it is a CLI-wide acceptance rule; put the underlying model or graph algorithm in core and consume its result here.
- Change `links.ts` only when the authored Markdown shape recognized by validation changes. Keep address parsing and local/federated lookup delegated to the resolver.
