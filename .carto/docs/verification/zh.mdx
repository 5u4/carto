Carto 验证两类不同的问题：常规 CI 判断已知行为在固定输入下是否仍然成立；Waza 评估则观察编码智能体面对一份陌生的小型代码库时，能否遵循 Carto 写作流程并留下有用的渲染文档。两者不能互相替代。

## 验证通道

| 要回答的问题 | 确定性单元测试 / CI | 确定性流水线测试 | Waza 真实模型评估 |
| --- | --- | --- | --- |
| 输入 | 仓库代码与固定测试夹具 | 手写文档集和脚本化源码变更 | 自然语言任务与陌生的限流器夹具 |
| 执行者 | TypeScript、shell 与 Vitest 进程 | 已构建的 `carto` 可执行文件和真实预览服务 | 由 `copilot-sdk` 驱动的 `claude-sonnet-4.6` |
| 防守范围 | 编译、类型、注释规范和局部行为契约 | CLI 的端到端状态迁移与渲染产物不变量 | 智能体能否遵循技能，产出双语、可构建且有源码依据的文档 |
| 可重复性 | 确定 | 确定 | 受模型输出影响；串行三次试验 |
| 是否阻断 PR | 是 | 是 | 否 |

这些通道分别由根脚本、CI 工作流与评估配置界定。`package.json:9-14` `.github/workflows/ci.yml:8-31` `scripts/lint-comments.sh:13-26` `evals/carto/eval.yaml:9-19`

## CI 与流水线工作流

拉取请求会走完一条有序且可复现的路径：

```text
GitHub Actions：check（Node 22）
├─ checkout；设置 pnpm 与 Node 缓存
├─ pnpm install --frozen-lockfile
├─ pnpm build
├─ pnpm typecheck
├─ pnpm lint
├─ pnpm test
└─ pnpm test:pipeline
   └─ Vitest 驱动 packages/cli/dist/index.js 与真实 preview 进程
```

CI 没有模型评估步骤，因此拉取请求变绿只依赖可复现的实现契约；Waza 通道衡量的则是[写作工作流](carto:authoring-workflow)所描述的智能体行为。

## 可观察的流水线状态迁移

流水线测试把手写夹具复制进临时根目录，驱动已经构建的 CLI，而不模拟命令内部逻辑。四次状态迁移都有明确的外部观察点：

| 状态迁移 | 触发与命令路径 | 必须观察到的结果 |
| --- | --- | --- |
| 未同步文档 → 完成验证与构建的站点 | `sync` → `validate` → `coverage` → `build` | 至少三个节点；coverage 扫描到包含三个文件的 code root；双语源码脚注与标识符；没有未解析的 `carto:` href |
| 静态产物 → 可访问的预览服务 | 启动 `preview`；请求 `/overview/feed/`；终止进程 | 返回含 `authorId` 的渲染内容，进程正常退出 |
| 新鲜 → 过期 → 定向刷新完成 | 替换 `src/user.ts`；`status`；安装新版 `user` 文档；`sync user`；`status`；`build` | 首次状态非零；刷新后恢复绿色；新旧概念同时存在于 HTML |
| 本地图 → 联邦图 | 加入文件型 glossary 与双语逻辑链接；`validate`；`build` | glossary 挂载到别名加哈希前缀，本地页面挂载到 `/self/`，跨集 URL 已解析，不残留 `carto:` href |

`tests/pipeline/carto-pipeline.test.ts:126-163` `packages/cli/src/commands/coverage.ts:4-27` `tests/pipeline/carto-pipeline.test.ts:165-193` `tests/pipeline/carto-pipeline.test.ts:195-220`

这条通道守住[新鲜度与作用域](carto:freshness-scope)中的状态变化，以及[渲染流水线](carto:rendering-pipeline)里的构建与预览生命周期。它证明“给定合格的手写文档，程序如何运行”，却不证明模型能写出这些文档。

## 真实模型评估测量什么

Waza 通过 `copilot-sdk` 串行执行三次试验，每次上限 900 秒，使用 `claude-sonnet-4.6` 和仓库内的 Carto 技能目录。`evals/carto/eval.yaml:1-19`

预先初始化的根目录声明 `en` 与 `zh`，并把 `codeRoot` 指向限流器夹具。任务不限定节点数量和 view 语法，但要求每种语言都留下两项可观察解释：一项 `TokenBucket.take` 决策 view，把 `refilled < 1` 分支与两个结果放在一起比较；一项实际执行的 `sampleApiLimitTrace()` 调用，包含按顺序返回的全部五条记录。随后，智能体必须先后完成正确性审计与独立的新鲜展示审计，才能执行 `sync`、`validate` 和 `build`。`evals/carto/fixtures/carto.json:1-6` `evals/carto/tasks/generate.yaml:11-44`

三次通过提供了跨模型运行的重复证据，但仍不能当作确定性的回归证明。

## 从夹具输入到评分器输出

评估边界现在会把夹具中的具体行为一直带到渲染契约：

```text
输入
├─ rate-limit-contract.ts：RateLimiter 与 RateLimitDecision
├─ token-bucket.ts：补充 → refilled < 1 → 拒绝或消耗
└─ api-request-limiter.ts：sampleApiLimitTrace()
        │
        ▼
任务：阅读 → 规划 view spine → 编写 en/zh → 两次审计 → sync → validate → build
        │
        ▼
每种语言都必须渲染的证据
├─ 决策 view
│  ├─ 拒绝：allowed false；remaining 向下取整；retry 向上取整
│  └─ 放行：allowed true； remaining 向下取整；retry 为零
└─ sampleApiLimitTrace()
   ├─ 1000  true   1     0
   ├─ 1000  true   0     0
   ├─ 1000  false  0  1000
   ├─ 1500  false  0   500
   └─ 2000  true   0     0
        │
        ▼
评分器
├─ 确定性程序
│  ├─ 在渲染后的 <main lang="en|zh"> 内查找语义 view
│  ├─ 验证两个决策结果和顺序、数值完全一致的 trace
│  ├─ 要求语言间决策/trace view 的类型、顺序与页面角色一致
│  └─ 拒绝缺失页面、空产物、flowchart LR 或未解析的 carto: href
└─ 在任务会话内执行、基于源码的模型量表
   └─ 判断实用性、覆盖度、必要性、非重复性、分布、仓库特异性、
      行为证据与语言间语义对齐
```

确定性评分器接受代码块、横向或纵向表格、定宽记录、figure、定义列表和列表等语义容器，不限定标题、节点数量、Mermaid 或某一种语法；它防守具体行为和语言间结构。prompt 量表恢复已经完成的任务会话，按六项基于源码的质量标准评估，并且必须以一次评分工具调用结束。任务定义义务，两类评分器分别覆盖机器稳定的不变量与面向开发者的定性价值。
