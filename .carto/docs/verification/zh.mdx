Carto 实际上验证两类不同的问题：常规 CI 判断已知行为在固定输入下是否仍然成立；Waza 评估则观察编码智能体面对一份陌生的小型代码库时，能否遵循 Carto 技能完成写作，并留下真正可渲染、可阅读的文档。前者通过不代表智能体会写文档，后者偶然成功也不能替代回归测试。

## 验证全景

根脚本把几条确定性通道分得很清楚：递归构建与类型检查、常规 Vitest 测试、注释规范检查，以及使用独立配置的流水线测试。`package.json:9-14`

CI 在 Node 22 环境中冻结依赖安装，然后依次执行构建、类型检查、lint、单元测试和流水线测试。工作流里没有模型评估步骤，因此拉取请求的绿色结果可复现，也不依赖模型本次生成了什么。`.github/workflows/ci.yml:8-31`

| 要回答的问题 | 确定性单元测试 / CI | 确定性流水线测试 | Waza 真实模型评估 |
| --- | --- | --- | --- |
| 输入 | 仓库代码与固定测试夹具 | 手写文档集和脚本化源码变更 | 自然语言任务与陌生的限流器夹具 |
| 执行者 | TypeScript、shell 与 Vitest 进程 | 已构建的 `carto` 可执行文件和真实预览服务 | 由 `copilot-sdk` 驱动的 `claude-sonnet-4.6` |
| 防守范围 | 编译、类型、注释规范和局部行为契约 | CLI 的端到端状态迁移与渲染产物不变量 | 智能体能否遵循技能，产出双语、可构建且有源码依据的文档 |
| 可重复性 | 确定 | 确定 | 受模型输出影响；配置为串行单次试验 |
| 是否阻断 PR | 是 | 是 | 否；CI 并未调用它 |

这种分工把实现回归与写作能力分开：CI 守住程序契约，模型评估衡量[写作工作流](carto:authoring-workflow)中的智能体行为。

## 流水线测试守住哪些状态迁移

流水线测试不模拟命令内部逻辑，而是把临时夹具交给已经构建好的 CLI，按真实运行顺序观察结果。完整场景覆盖以下状态。`tests/pipeline/carto-pipeline.test.ts:116-226`

1. **未同步的手写文档 → 合法、覆盖完整的站点。** 首次裸 `sync` 为节点源码建立指纹；随后 `validate` 必须通过，`coverage` 必须从配置的代码根统计出全部三个文件；`build` 产物须同时包含中英文源码脚注、源码标识符，且不能残留 `carto:` href。`tests/pipeline/carto-pipeline.test.ts:137-163`
2. **静态产物 → 可访问的预览服务。** 测试启动真实预览进程，请求嵌套的 feed 页面，确认内容已渲染，并验证进程收到终止信号后正常退出。`tests/pipeline/carto-pipeline.test.ts:165-172`
3. **新鲜 → 过期 → 定向刷新完成。** 替换 `src/user.ts` 后，`status` 必须以非零状态退出。测试随后只放入 `user` 节点的新版文档，执行 `sync user`，要求状态恢复绿色，再次构建并确认新旧概念都出现在产物中。`tests/pipeline/carto-pipeline.test.ts:174-193`
4. **本地图 → 联邦图。** 清单新增文件型 glossary 文档集，两个语言页面都加入跨文档集逻辑链接。此后验证和构建仍须成功；产物须把 glossary 挂载到“别名 + 哈希”前缀下，把自身页面挂载到 `/self/`，并把跨集链接改写成最终 URL，不得遗留 `carto:` href。`tests/pipeline/carto-pipeline.test.ts:195-220`

这条确定性端到端防线同时覆盖[新鲜度与作用域](carto:freshness-scope)中的状态变化，以及[渲染流水线](carto:rendering-pipeline)里的构建和预览生命周期。它证明“给定合格的手写文档，程序会如何运行”，却不证明模型能写出这些文档。

## 真实模型评估测量什么

Waza 套件是一条轻量端到端 smoke：通过 `copilot-sdk` 调用 `claude-sonnet-4.6`，使用仓库内的 Carto 技能目录，单次试验超时 900 秒且不开并行。`evals/carto/eval.yaml:1-19`

任务把一个干净的文档根交给模型，要求它在需要时初始化 Carto，读完三个夹具文件，自行判断“最小但有用”的节点集合，为每个节点写带 frontmatter 的 `en` 与 `zh` 页面，适当使用逻辑链接，在首次同步前完成审计，最后让 `sync`、`validate` 和 `build` 全部成功。任务刻意不规定节点数量，因为被测对象还包括文档结构判断，而不只是能否生成文件。`evals/carto/tasks/generate.yaml:1-53`

因此它是本地运行、依赖真实模型输出的评估，而不是 CI 门禁：CI 没有 eval 命令，这份配置却明确选定了模型与执行器。单次通过只说明某一次智能体运行走完了流程，不能当作确定性的回归证明。

## 夹具与评分器之间的契约

夹具规模很小，但三个文件分别迫使文档覆盖抽象契约、核心实现和调用边界：

- `RateLimitDecision` 约定是否放行、剩余整数令牌数和重试等待时间；调用方依赖的抽象入口是 `RateLimiter.take(nowMs)`。`evals/carto/fixtures/rate-limiter/src/rate-limit-contract.ts:1-8`
- `TokenBucket` 初始为满桶；时间倒退时抛错；令牌随时间连续补充但不超过容量；不足一个令牌时拒绝并计算等待时间，否则消耗一个令牌后放行。`evals/carto/fixtures/rate-limiter/src/token-bucket.ts:3-47`
- API 层固定使用容量为二、以每秒一个令牌的速率连续补充的桶，把完整决策适配成布尔值，并以重复及递增时间戳生成五步示例轨迹。`evals/carto/fixtures/rate-limiter/src/api-request-limiter.ts:4-18`

任务契约要求模型读懂并记录这些源码。文件评分器先要求 `carto.json` 存在，程序评分器再检查可观察的构建产物。`evals/carto/tasks/generate.yaml:42-53` 具体条件包括：至少存在一个节点、每个节点旁都有英文和中文页面、`dist-site` 存在且含 HTML、渲染结果出现 `TokenBucket` 与 `sampleApiLimitTrace`，同时 HTML 中没有未解析的 `carto:` 链接。`evals/carto/graders/check_build.py:7-43`

调整评估时应沿这条边界下手：想改变写作问题，就改夹具；想改变智能体必须执行的步骤，就改任务；只有外部可观察的成功条件变化时才改评分器。只在提示词里加强文案要求，不会自动变成确定性断言；若要加强评分器，也应选择稳定的产物不变量，而不是绑定某一种节点拆分方式。
