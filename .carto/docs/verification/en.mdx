---
title: Verification strategy
description: How deterministic CI and pipeline checks complement Carto's real-model authoring evaluation.
---

Carto verifies two different things. Ordinary CI asks whether known behavior still works under repeatable inputs. The Waza evaluation asks whether a coding agent can follow Carto's authoring workflow on a small unfamiliar codebase and leave useful rendered documentation. Neither result substitutes for the other.

## Verification lanes

| Question | Deterministic unit / CI checks | Deterministic pipeline test | Waza real-model evaluation |
| --- | --- | --- | --- |
| Input | Checked-in code and fixed test fixtures | Hand-written doc sets plus scripted source mutations | A natural-language task and an unfamiliar rate-limiter fixture |
| Actor | TypeScript, shell, and Vitest processes | The built `carto` executable and a live preview server | `copilot-sdk` running `claude-sonnet-4.6` |
| Defended behavior | Compilation, types, comment policy, and focused contracts | End-to-end CLI state transitions and rendered-site invariants | Whether an agent follows the skill and produces bilingual, buildable, code-grounded docs |
| Repeatability | Deterministic | Deterministic | Model-dependent; three serial trials |
| Pull-request gate | Yes | Yes | No |

The lane definitions come from the root scripts, CI workflow, and evaluation configuration. `package.json:9-14` `.github/workflows/ci.yml:8-31` `scripts/lint-comments.sh:13-26` `evals/carto/eval.yaml:9-19`

## CI and the pipeline workflow

The pull-request path is an ordered, reproducible workflow:

```text
GitHub Actions: check (Node 22)
├─ checkout; set up pnpm and Node cache
├─ pnpm install --frozen-lockfile
├─ pnpm build
├─ pnpm typecheck
├─ pnpm lint
├─ pnpm test
└─ pnpm test:pipeline
   └─ Vitest drives packages/cli/dist/index.js and a real preview process
```

`.github/workflows/ci.yml:8-31` `package.json:9-14` `tests/pipeline/carto-pipeline.test.ts:8-24` `tests/pipeline/carto-pipeline.test.ts:116-125`

There is no model-evaluation step in CI. A green pull request therefore defends implementation contracts without depending on a fresh model response; the Waza lane instead measures the agent behavior described in the [authoring workflow](carto:authoring-workflow).

## Observable pipeline state transitions

The pipeline test copies hand-written fixtures into a temporary root and exercises the built CLI rather than mocking command internals. Its assertions define four observable transitions:

| Transition | Trigger and command path | Required observation |
| --- | --- | --- |
| Unsynced docs → validated, built site | `sync` → `validate` → `coverage` → `build` | At least three nodes; coverage scans a three-file code root; bilingual source footnotes and identifiers; no unresolved `carto:` href |
| Built site → live preview | Start `preview`; request `/overview/feed/`; terminate process | Rendered `authorId` is served and the process exits cleanly |
| Fresh → stale → refreshed | Replace `src/user.ts`; `status`; install revised `user` docs; `sync user`; `status`; `build` | First status is nonzero; refreshed status is green; old and new concepts coexist in HTML |
| Local graph → federated graph | Add file-backed glossary and bilingual logical links; `validate`; `build` | Glossary mounts under alias-hash, local pages under `/self/`, cross-set URL resolves, no `carto:` href remains |

`tests/pipeline/carto-pipeline.test.ts:126-163` `packages/cli/src/commands/coverage.ts:4-27` `tests/pipeline/carto-pipeline.test.ts:165-193` `tests/pipeline/carto-pipeline.test.ts:195-220`

This lane defends the state changes explained in [freshness and scope](carto:freshness-scope) and the build/preview lifecycle in the [rendering pipeline](carto:rendering-pipeline). It proves what the executable does with valid hand-written docs; it does not prove that a model can author them.

## What the real-model evaluation measures

Waza runs three non-parallel trials through `copilot-sdk`, each with a 900-second cap, using `claude-sonnet-4.6` and the repository's Carto skill directory. `evals/carto/eval.yaml:1-19`

The pre-initialized root declares `en` and `zh` and points `codeRoot` at the rate-limiter fixture. The task leaves node count and view syntax open, but requires two observable explanations in every locale: one structural `TokenBucket.take` decision view comparing the `refilled < 1` branch with both outcomes, and one executed `sampleApiLimitTrace()` invocation with all five returned records. The agent must then run the correctness audit and a separate fresh presentation audit before `sync`, `validate`, and `build`. `evals/carto/fixtures/carto.json:1-6` `evals/carto/tasks/generate.yaml:11-44`

Three successful trials provide repeated evidence across model runs; they do not become a deterministic regression proof.

## Fixture-to-grader input and output

The evaluation boundary now carries concrete behavior from fixture to rendered contract:

```text
inputs
├─ rate-limit-contract.ts: RateLimiter and RateLimitDecision
├─ token-bucket.ts: refill → refilled < 1 → deny or spend
└─ api-request-limiter.ts: sampleApiLimitTrace()
        │
        ▼
task: read → map view spine → author en/zh → audit twice → sync → validate → build
        │
        ▼
required rendered evidence in each locale
├─ decision view
│  ├─ deny:  allowed false; floor remaining; ceil retry
│  └─ allow: allowed true;  floor remaining; zero retry
└─ sampleApiLimitTrace()
   ├─ 1000  true   1     0
   ├─ 1000  true   0     0
   ├─ 1000  false  0  1000
   ├─ 1500  false  0   500
   └─ 2000  true   0     0
        │
        ▼
graders
├─ deterministic program
│  ├─ find semantic views inside rendered <main lang="en|zh">
│  ├─ verify both decision outcomes and exact ordered trace records
│  ├─ require matching locale kind, order, and page role for decision/trace views
│  └─ reject missing pages, empty output, flowchart LR, or unresolved carto: hrefs
└─ in-session source-grounded model rubric
   └─ judge utility, coverage, necessity, nonduplication, distribution,
      repository specificity, behavioral evidence, and locale alignment
```

The deterministic grader accepts semantic containers such as code blocks, row- or column-oriented tables, fixed-width records, figures, definition lists, and lists without prescribing headings, node count, Mermaid, or one exact syntax. It defends concrete behavior and locale structure. The prompt rubric resumes the completed task session, evaluates six source-grounded quality criteria, and must finish with exactly one grading tool call. The task owns obligations; the two graders cover machine-stable invariants and qualitative developer value separately.
