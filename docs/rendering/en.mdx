---
title: Rendering
description: How a carto doc root becomes a Starlight-on-Astro site through a two-phase render over one core Graph.
---

A carto doc root is not a website. It is a tree of `<id>/<locale>.mdx` files plus a `carto.json` manifest — the raw material the [links](carto:links) and [freshness](carto:freshness) subsystems reason about. The `@carto/template` package turns that material into a Starlight-on-Astro site through one deep rendering interface: `buildSite(docRoot)` and `previewSite(docRoot, options)`.

`carto build` calls the first operation. `carto preview` calls the second and never rebuilds.

## Transactional build lifecycle

Each build owns one unique directory under the operating system's temporary directory. The rendering module hides that workspace from the CLI and gives Astro private locations for every generated or writable input:

```text
<temporary-root>/
  astro.config.mjs
  node_modules/...
  src/
    content.config.ts
    content/docs/...
  .astro/cache/...
  output/...

```

The lifecycle has four ordered steps:

1. Create the workspace and its private source, dependency view, cache, and output paths.
2. Materialize the carto graph into `src/content/docs`; write workspace-local Astro and content configuration that reuse the installed template; and expose installed plus doc-root dependencies without modifying either source tree.
3. Invoke Astro's installed CLI with the temporary `--root`, workspace config, and temporary `--outDir`.
4. Only after Astro succeeds, copy the completed output to a same-filesystem staging directory and replace `<doc-root>/dist-site`. If Astro or publication fails, the previous `dist-site` remains available.

The temporary workspace is removed in a `finally` path. There is no lock, shared generated directory, or persistent cache. In particular, build never writes `@carto/template/src/content/docs`; the installed package is configuration and executable code, not a workspace.

## Materialization

`materialize(docRoot, contentDir)` loads one `Graph` through `loadGraph(root)`, then writes only to the caller-provided content directory. The graph contains the root manifest and every federated doc-set (`{ federated, root, byHash }`).

If the root manifest has no nodes and the graph is not federated, materialization writes a single onboarding `index.mdx`. It tells the user to ask their agent to document the code, then run `carto build` and `carto preview`.

Otherwise the render loop iterates **doc-set × node × site locale**. For every cell it:

1. Selects the requested locale when the doc-set provides it, or warns and falls back to that doc-set's default locale.
2. Reads `<docRoot>/docs/<id>/<locale>.mdx`.
3. Rewrites resolvable `carto:` links with `resolveCartoLink`; an empty label is filled from the target title with target-default-locale and id fallbacks.
4. Injects the page's freshness banner when its status is stale or missing.
5. Writes the page below the private content directory.

The target path combines a locale prefix, a federated doc-set prefix, and the node's root chain. The site-default `overview` page of the root doc-set becomes `src/content/docs/overview.mdx`; a Chinese `auth` page from a federated `web` doc-set becomes `src/content/docs/zh/web/auth.mdx`. Freshness is collected once per doc-set with `statusReport` against its resolved code root.

## Preview lifecycle

`previewSite` first requires `<doc-root>/dist-site` to exist. It then invokes Astro preview against exactly that output, with no materialization or build step. The default address is `http://127.0.0.1:4321/`; explicit host and port values are forwarded to Astro and printed before serving. `SIGINT` and `SIGTERM` received by Carto are forwarded to the child process and treated as a clean shutdown; a signal delivered independently to Astro is surfaced as a preview failure.

## Staleness banner

`injectStalenessBanner` is a pure string transform over one page's MDX
(`packages/template/src/staleness-banner.ts:3`). Its rules:

- **No-op unless stale or missing.** `fresh`, `unsynced`, or `undefined` status
  returns the input unchanged (`packages/template/src/staleness-banner.ts:4`). The
  `state` field comes from `NodeStatus` (`packages/core/src/status.ts:15`), owned by
  [freshness](carto:freshness).
- **Frontmatter-aware.** It matches the leading `---\n…\n---` block; a page without
  frontmatter is left alone (`packages/template/src/staleness-banner.ts:5`).
- **Idempotent.** If the frontmatter body already has a `banner:` key it bails, so
  re-running materialize never double-stamps (`packages/template/src/staleness-banner.ts:8`).
- **Content.** It inserts a Starlight `banner:` frontmatter key whose message lists
  the changed source files (`<code>…</code>`) under "changed since this page was
  written" and missing ones under "no longer exist"
  (`packages/template/src/staleness-banner.ts:11`, message at
  `packages/template/src/staleness-banner.ts:15`). Quotes and backslashes in the
  message are escaped so the YAML string stays valid
  (`packages/template/src/staleness-banner.ts:10`).

Starlight renders that `banner:` key as a site-wide banner atop the page, so a
stale page announces its own staleness at read time.

## Workspace-aware `astro.config.mjs`

The installed Astro config keeps two roots distinct. `CARTO_ROOT` identifies the user's doc root for graph and user-configuration loading. `CARTO_WORKSPACE` identifies Astro's temporary root, so `srcDir` and `cacheDir` stay private to one build. The CLI's explicit `--outDir` selects either temporary build output or the existing preview output.

The remaining behavior is stable across workspaces: redirects come from `buildGraphRedirects`, the Markdown pipeline applies `remarkJoinCjkLines`, and the integrations are Mermaid plus Starlight. Starlight receives `mergeStarlight(user.starlight ?? {}, { locales, sidebar })`, preserving user theme configuration while carto owns graph-derived navigation.

## Config derivations (`site-config.ts`)

- **`buildLocales`** maps each manifest locale to a Starlight locale entry, keying
  the **default locale as `root`** (Starlight's convention for the un-prefixed
  locale) and others by their own code (`packages/template/src/site-config.ts:7`).
- **`buildGraphSidebar`** builds the root doc-set's sidebar, then appends every other
  doc-set (sorted by prefix) as its own titled group
  (`packages/template/src/site-config.ts:33`). Within a doc-set, `entryFor` gives a
  node with children a group whose **first item is the parent itself** as a leaf,
  followed by its children — so a parent is both a heading and a clickable page
  (`packages/template/src/site-config.ts:82`). Group labels come from the doc-set's
  home-node title via `docSetLabel` (`packages/template/src/site-config.ts:44`).
- **`buildGraphRedirects`** redirects `/` (and `/<locale>/`) to the root doc-set's
  home node, so the bare site URL lands on a real page
  (`packages/template/src/site-config.ts:62`, via `buildRedirects` at
  `packages/template/src/site-config.ts:51`).
- **`collectGraphTitles`** reads each page's frontmatter `title:` and stores it
  keyed `hash:id:locale` (`packages/template/src/site-config.ts:96`, extraction at
  `packages/template/src/site-config.ts:114`). This is the map both the sidebar and
  materialize's empty-label link filling consult.
- **`loadUserConfig` + `mergeStarlight`** let a project drop a `carto.config.mjs`
  that default-exports `{ starlight }` (`packages/template/src/site-config.ts:144`).
  The merge order matters: carto seeds `title: 'Carto'`, spreads the user options
  over it, then **force-owns `locales` and `sidebar`** last
  (`packages/template/src/site-config.ts:174`). A user can theme freely but cannot
  break navigation — the two structural keys carto derives from the graph always win.

## CJK line joining (`remark-join-cjk.ts`)

Markdown treats a single newline as a soft break, which for CJK text inserts an
unwanted space between characters. `remarkJoinCjkLines` walks every text node and
collapses a soft break **only when it sits between two adjacent CJK characters**
(`packages/template/src/remark-join-cjk.ts:39`, join at
`packages/template/src/remark-join-cjk.ts:25`). The regex fires on the CJK ranges
plus em-dash and ellipsis, and requires a CJK char on both sides
(`packages/template/src/remark-join-cjk.ts:23`) — so `你好\n世界` becomes `你好世界`
while `hello\nworld` and mixed CJK/Latin boundaries keep their space. This is why the
[zh](carto:overview) pages authored with hard-wrapped source lines still render as
continuous prose.
