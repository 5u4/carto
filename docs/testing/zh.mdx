carto 的测试沿着一条断层线组织：**每套测试守护什么**。两套测试，两份契约，互不重叠。

## 两套测试，按守护目标划分

**单元测试**守护各个模块本身的正确性——schema、哈希器、链接解析器、节点树。它由
`vitest.config.ts` 配置，匹配 `packages/**/*.test.ts`
（`vitest.config.ts:11`），并将 `@carto/core` 别名指向其 TypeScript 源码，因此测试无需
构建步骤即可直接针对 `packages/core/src` 运行（`vitest.config.ts:7`）。它是确定性的，且
不访问网络。用 `pnpm test` 运行。

**流水线测试**守护这些模块*之间的接缝*——即 `sync`、`validate`、`coverage`、`build`、
`status` 与联邦（federation）确实能组合成一个可用的文档系统。它由
`vitest.pipeline.config.ts` 配置，匹配 `tests/pipeline/**/*.test.ts`
（`vitest.pipeline.config.ts:11`），并将测试与钩子的超时都提高到 120s
（`vitest.pipeline.config.ts:12-13`），因为每个阶段都会以子进程方式启动真实 CLI。用
`pnpm test:pipeline` 运行。

两份配置共享同一个 `@carto/core` → 源码 的别名（`vitest.pipeline.config.ts:7`），因此两套
测试都不依赖预先构建的 core 产物。

技能*质量*——某个 agent 是否真的遵循了文档撰写技能——在这里根本不算一套测试。它属于
[evals](carto:evals) 这一层，会调用真实模型，因此仅限本地运行，绝不接入 CI。本页只讲这两套
确定性测试；evals 是第三层、非 CI 的度量层。

## 流水线测试就是那块白板

[carto CLI](carto:cli) 的整体都由这一个测试来演练：
`tests/pipeline/carto-pipeline.test.ts`。它是核心中枢——一个 `it` 块，在**手写的
fixtures** 上走完整条文档循环，驱动的是*真实构建出来的二进制*，而非导入函数。

它从不直接接触 `@carto/core`。它把已编译的 CLI 定位到
`packages/cli/dist/index.js`（`carto-pipeline.test.ts:8-10`），并通过
`spawnSync(process.execPath, [cartoCli, ...args])` 调用它
（`carto-pipeline.test.ts:18-24`），捕获退出状态、stdout 与 stderr。因为它驱动的是构建
产物，一个 `beforeAll` 守卫会在二进制缺失时失败——先运行 `pnpm build`，再运行
`pnpm test:pipeline`（`carto-pipeline.test.ts:90-95`）。

:::note
无 LLM、无密钥、无网络。每个 fixture 都是手工签入的，每条断言都是确定性的，因此流水线测试可
在 CI 中运行。
:::

### 它所走的循环

每个阶段都把 fixtures 复制进一个全新的 `mkdtemp` 根目录并断言可观测结果，全部包在
`try/finally` 中，最终删除临时根目录（`carto-pipeline.test.ts:100-106`，清理见
`carto-pipeline.test.ts:189-190`）。

**Sync → validate → 节点计数。** 它复制 `sample-app/src` 与 `doc-set`，运行
`carto sync`，要求 `carto validate` 为绿，再断言至少存在三个 node 目录
（`carto-pipeline.test.ts:107-119`）。

**Coverage 走的是代码，而非文档。** `carto coverage` 必须报告 `/ 3 files`，证明
[coverage](carto:coverage) 走的是代码根，而非文档根
（`carto-pipeline.test.ts:121-123`）。

**Build 与 preview 演练真实产物。** `carto build` 必须渲染真实符号 `authorId`、
`buildFeed`，且不留下未解析的 `carto:` href（`carto-pipeline.test.ts:125-131`）。随后测试
在空闲的 localhost 端口启动 `carto preview`，抓取 `/overview/feed/`、检查返回的 HTML，
并干净地终止预览进程（`carto-pipeline.test.ts:133-140`）。

**陈旧检测。** 它修改 `src/user.ts` 并要求 `carto status` 失败。复制刷新后的正文并运行
定向的 `carto sync user` 后，status 恢复为绿；重建结果同时包含新符号 `handle` 与原有符号
（`carto-pipeline.test.ts:142-161`）。

**联邦。** 它注册第二个 `glossary` doc-set，并在两种语言中加入
`carto:glossary/terms` 链接（`carto-pipeline.test.ts:163-177`）。最终构建必须把联邦页
挂载在 `glossary-<8 位十六进制>` 下，把根页面挂载在 `/self` 下，并解析跨 doc-set URL
（`carto-pipeline.test.ts:178-188`）。

### 为什么要驱动二进制

导入函数测的是单元；启动二进制测的是产品。流水线测试是唯一一处以用户运行的方式演练*已组合*系统
的地方——真实的 `carto` 进程、磁盘上真实的 fixture 文件、真实的 HTML 输出。它是 [CLI](carto:cli)
所暴露的每一条命令之下的安全网。
